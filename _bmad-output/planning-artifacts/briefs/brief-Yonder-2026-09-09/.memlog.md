topic: Yonder: agent-driven customizable desktop companion for local and remote automation
updated: 2026-09-09T14:17
---

- (decision) Create a lightweight local desktop companion that external local or remote agents can drive.
- (decision) Core vision includes customizable character appearance, standardized interaction actions with generated animations, computer/browser use, local commands, code generation, and record/replay.
- (assumption) Use an Ego-style thin companion/tool layer connected to external agents; exact Ego-lit reference and protocol remain to be clarified.
- (decision) Initial users are PC-based knowledge workers; most target tasks involve office documents or browser workflows.
- (override) Replace the narrower knowledge-worker segment with white-collar workers who rely on PCs for daily work; document operations are the densest scenario, followed by desktop software and browser operations.
- (override) Position Yonder as an agent tool rather than an AI assistant: a local perception-and-action layer between the user's PC and cloud agents, desktop agents, or agent CLIs.
- (decision) The core product purpose is to collect and expose user-controlled personal work context for a companion personal-context product; the desktop pet is its visible interaction and status surface.
- (decision) Personal-context capture priority is: document content, browsing history/context, user action sequences, then current window and application; other context types remain in the broader vision.
- (assumption) MVP should deliver context sources incrementally rather than enable unrestricted collection of every source at once, due to permissions, privacy, and application-adapter scope.
- (decision) Default data model: user-authorized personal work context is synchronized to the companion cloud personal-context product for cross-device access and long-term memory.
- (decision) Because cloud synchronization is the default, identity, consent, visibility, deletion, and sensitive-data exclusion are foundational product requirements.
- (override) Context capture is off by default and never continuously monitors the user; collection starts only when the user explicitly begins a Record session.
- (decision) Record sessions capture authorized work context and action sequences; Replay lets an agent reuse the resulting workflow and context.
- (lock) MVP Record output is a unified timeline containing action events, screenshots or document references, and application/window state, synchronized to the cloud; the consuming agent plans Replay.
- (decision) Exclude automatic workflow generalization, a visual workflow editor, and built-in parameterization from MVP.
- (decision) ego-lite research: its compatibility model is Agent Skill plus a host-installed CLI that scripts an app-owned runtime; it does not use MCP as the primary interface, and remote agents require a host bridge.
- (direction) Proposed Yonder MVP integration: Yonder Agent Skill plus local CLI/runtime contract, with MCP as a later adapter and an authenticated cloud-to-device bridge for remote agents.
- (override) Agent Skills are not the cloud connection mechanism. Yonder differentiates from ego-lite through a first-class authenticated cloud-to-device channel for remote agent access, while the local runtime enforces consent and permissions.
- (lock) Yonder permits third-party agents to connect; it is an open agent tool layer rather than an exclusive client for the first-party personal-context cloud product.
- (decision) Third-party access requires stable capability discovery, scoped authorization, connection visibility, and revocation controlled by the user.
- (lock) Authorized third-party cloud agents may both query synchronized historical personal context and submit tasks to an online user device.
- (decision) Historical-context access and live device operation must be separate permission scopes; granting one never implies the other.
- (lock) Initial third-party scopes: context:read, device:observe, device:control, browser:control, command:execute, and record:manage; sensitive actions require desktop confirmation.
- (direction) Adapt ego-lite Task Space into a durable Yonder task container with Agent identity, scopes, lifecycle, resources, timeline, artifacts, audit, pause, takeover, and cancellation.
- (assumption) MVP can parallelize isolated browser tasks, but foreground CUA must be serialized because desktop focus, mouse, and keyboard are shared OS resources.
- (lock) CUA and BUA are separate execution paths beneath a shared Task Space lifecycle, permission, event, audit, interruption, and handoff model.
- (lock) MVP BUA reuses ego-lite and ego-browser as the browser execution backend; Yonder will not build its own managed Chromium or browser automation engine.
- (decision) Yonder wraps ego-lite browser work in its shared Task Space, permission, context-sync, status-mapping, audit, and desktop-pet presentation layers.
- (lock) MVP launches on both Windows and macOS.
- (decision) CUA exposes a shared cross-platform capability set while reporting platform-specific capabilities explicitly; parity is not assumed where OS primitives differ.
- (lock) MVP structured desktop integrations cover Microsoft Word, Excel, PowerPoint, WPS, macOS Finder, and Windows File Explorer; other applications remain available through generic CUA without structured-context guarantees.
- (direction) Evaluate open-computer-use as the replaceable MVP CUA backend; adopt accessibility-first, pixels-second, look-act-verify, background-actions-first, and separately gated foreground input.
- (decision) Use UI-TARS only for visual fallback and event-stream design reference, and Microsoft UFO for Windows UIA/Win32/COM and Office-specific action reference; do not embed either full Agent framework.
- (lock) MVP desktop-pet customization supports importing a conforming animation asset pack mapped to standard states; AI generation of character animations is excluded.
- (lock) MVP success means running the primary end-to-end path; quantitative scale, coverage, and reliability targets follow after the trunk flow is proven.
- (direction) Prioritize evaluation of Qwen Code's native cua-driver for Yonder CUA because it covers Windows/macOS accessibility trees, screenshots, input, sessions, recording, and trajectory replay; use QwenLM/open-computer-use as the lighter MCP/CLI contract reference.
- (lock) Yonder needs only a model-agnostic local CUA execution engine; it will not embed an Agent, planner, model loop, or Qwen Code runtime.
- (decision) Use Qwen cua-driver or its low-level platform runtime as the primary reuse target; treat Qwen open-computer-use only as a protocol/packaging reference and OSWorld only as an evaluation harness.
- (direction) CUA shortlist: Qwen cua-driver remains the dual-platform default; trycua/cua-driver is the strongest challenger but its cross-platform Rust port requires validation. Compare both behind the same minimal Yonder contract and ship only one backend.
- (lock) Qwen cua-driver and trycua cua-driver are the two CUA backend candidates and must undergo the same black-box comparison on Windows and macOS before selection; MVP will ship only the winner.
- (lock) All project planning and generated documents must be written in Chinese.
- (override) Yonder 实现范围仅为桌面插件应用；个人上下文云服务和云端 Agent 平台是外部系统，Yonder 只实现客户端连接。
