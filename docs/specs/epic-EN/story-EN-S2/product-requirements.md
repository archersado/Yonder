# EN-S2 产品需求

## 问题与目标

Yonder 需要一套可信的发布与分发流程，确保 desktop、CLI、MCP、IPC 协议、SQLite 迁移和 Driver manifest 在同一固定版本内交付，并在升级前后保持数据可恢复。

## 范围与非目标

- 范围：双平台安装包、签名与公证、版本固定、升级前备份、dev/stable 通道和发布证据。
- 非目标：不实现云端服务端、账号系统、自动更新服务器、第三方分发平台集成或双发布通道。

## 验收条件

- REL-01：一次发布包含 desktop、CLI、MCP、IPC 协议、迁移和 Driver manifest，版本固定，不使用 `latest`。
- REL-02：macOS 包通过签名与 notarize，Windows 包通过 code-sign，并保留可复验的结构化证据。
- REL-03：升级前自动备份数据库；迁移失败可回退到旧版本且数据不丢失。
- REL-04：只提供 `dev` 与 `stable` 两个通道，通道元数据与实际产物一致。
- REL-05：发布包不含密钥、凭据、用户数据或完整日志正文。
- REL-06：发布证据记录版本、提交、构建环境、签名校验结果、迁移测试结果和双平台安装/卸载样本。

## 需求来源与验收映射

| 类型 | 来源 | 对应验收 |
|---|---|---|
| 原始需求 | 产品简报「MVP 主干链路」：安装 Yonder、登录账号并导入资源包 | REL-01～04、06 |
| 原始需求 | 产品简报「待决策事项」：安装包签名与分发方式 | REL-01～04、06 |
| 补充材料 | CUA 驱动对比要求覆盖安装、签名和系统权限 | REL-01、02、06 |
| 架构约束 | 架构主干「非功能与发布」：版本固定、迁移备份、notarize/code-sign、双通道 | REL-01～06 |

## 待审建议

首版只支持 macOS `.app` 与 Windows 安装包，不引入通用自更新服务；发布证据使用本地结构化 JSON 和原生命令输出，不写入任务数据库。
