## 验收与依赖

产品来源：产品简报「Task Space 与权限模型」「MVP 主干链路 7–9」、补充材料「CUA 与 BUA 的 Task Space」。架构来源：ARCHITECTURE-SPINE「任务、状态与恢复」「个人上下文」。以下是需求归属拆解，不新增运行时协议或状态所有者。

| 产品信息/行为 | 事实写入方 | 本模块责任 | 消费方与限制 |
|---|---|---|---|
| 发起 Agent、授权范围与授权引用 | AG 的可信接入用例 | TM-S1 保存任务绑定与可审计引用 | AG 每次重新校验有效授权；历史记录不是长期通行证 |
| 当前状态、步骤、结果、错误 | 可信 Application/执行用例 | TM-S1 当前快照；TM-S5 保留历史事实 | DS 展示、AG 查询，不从自然语言推断成功 |
| 文件/窗口/浏览任务等资源引用 | 对应能力 Adapter 经 Application | TM-S1 记录稳定引用与可用性；TM-S2 管资源占用 | 文件/窗口/标签页仍归原应用，不复制 ego-lite Task Space |
| 等待原因、资源冲突 | TM-S2/控制用例 | TM-S1 查询契约，TM-S2 决定准入 | DS 明确等待，不能伪报执行中；瞬态占用不成为第二任务事实源 |
| 暂停、取消、用户接管 | 用户经 DS/AG，执行器确认 | TM-S3 控制语义，TM-S1 提交状态，TM-S5 审计 | 停止确认前不释放，授权来源不能由请求自报 |
| 恢复信息、显式继续 | TM-S4 与外部 Agent | TM-S1 保留恢复事实，TM-S4 重新观察后执行 | 不在 Yonder 内做语义 replan，不重放未知动作 |
| 时间线、产物、审计、用户结果确认 | 可信执行和用户交互用例 | TM-S5 结构化历史、产物引用及结果确认记录 | DS-S2 展示，AG 授权查询；记录不是自动录制屏幕 |
| 全量忙碌与未知 | TM-S1 完整状态查询，TM-S2 执行占用提供约束 | TM-S1 定义汇总契约，不能把未知视为空闲 | DS 控制桌宠，不由分页或当前选择推算 |

TM-S1 与 TM-S5 分别负责最新状态查询和历史/产物查询，但必须共同评审写事务与事件契约。不是两个独立任务库，不为了拆 Story 引入完整 Event Sourcing。基础元数据不得先落成无法保存原需求历史的方案。

## 本轮拆解顺序

1. TM-S1：先确定记录/查询事实和状态展示契约，关闭元数据与全量忙碌两个缺口。
2. TM-S2：在明确任务事实契约后设计资源身份、派发前检查、停止确认和状态/占用一致性；复用已验证的核心代码，不提前宣称真实执行器完成。
3. TM-S3：指定任务暂停/取消与桌面接管，依赖真实停止能力。
4. TM-S4：用户显式归还、重新 Observe 后继续；不做自动恢复或语义规划。
5. TM-S5：与 TM-S1 同期完成历史记录边界设计，再按真实执行/控制能力接入验收；不能等到最后才补不可恢复的审计数据。

每个 Story 依次完成三份设计再生成 Proposal，不能用同一混合 Change 跨模块逐段堆实现。

按每个 Story 验收；不以库层测试代替原生双平台闭环。跨模块依赖只通过既有 Port/Application/Protocol，不因 Epic 划分改变 Cargo 依赖方向。
