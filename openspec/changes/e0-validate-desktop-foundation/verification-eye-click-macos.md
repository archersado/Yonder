# DS-S1 右侧眼睛点击独立 Verification Goal

Story：DS-S1；OpenSpec：e0-validate-desktop-foundation；日期：2026-09-13。

依据：增量规格「点击唤醒」，用户要求点击双眼入口唤醒。状态：用户真实桌面手动确认可唤醒；自动化点击仍未通过。不 Archive。

## 范围与工具

沿用 PID 32717、窗口24408的当前小尺寸素材构建。仅扩展 check-wake-visible.swift 的可选 `--click-right-eye` 验证模式；默认托盘模式保留，不改变桌宠产品行为。右侧形态用截图确认眼睛在入口局部[49,38]，工具读取当前窗口坐标后点击该位置，不调用 pet_wake，不通过托盘替代。

最终工具先检查系统发送事件权限、窗口 onscreen、56×112尺寸及完全位于主屏范围；不满足即停止。该模式只用于人工确认的右侧主屏形态，不是其他边缘或多屏通用点击工具。最终鼠标序列包含移入、100ms间隔、单击计数1、按下和50ms后松开。此序列的原生成功验证仍缺失。

## 尚待定位

- 稳定坐标下完整鼠标序列是否能到达WebView及pointerdown处理。
- 未激活窗口的首击语义：本地锁定依赖 tauri-utils 2.9.3 默认 accept_first_mouse=false，文档注释说明它控制未激活窗口点击是否透传WebView。当前配置未设置该项，是待验证因素；本轮没有未经原生对照就修改配置。
- 通过一次真实眼睛点击恢复前，不关闭点击唤醒验收；历史托盘成功记录仍有效但不能替代。

Windows已由用户暂缓，仍保留完成门禁。本轮Swift编译通过，失败及停止路径得到真实运行验证；产品二进制未修改。

## 完整事件序列与激活对照续验

`right-eye-click-20260913-sequence-retry/`：主屏内[1703,785]执行完整移入/按下/松开序列，仍未恢复，退出6；因此短促down/up不是已证实的唯一原因。

工具新增仅诊断用 `--click-right-eye-active`：先请求激活并要求isActive为true，否则停止。`right-eye-active-control-20260913/`显示原始isActive=false，activate请求返回true，300ms后仍false，退出4，未发送对照点击。该记录不支持“激活后点击仍失败”结论，也不能确认accept_first_mouse的因果性。

已请求用户在能看到双眼的普通桌面保持稳定，准备后继续；没有在坐标不稳定时反复发送输入。产品代码仍未修改。

## 用户手动验收（2026-09-13）

用户切换至可见普通桌面后明确反馈：**“能被唤醒，我测试了”**。据此记录当前本机眼睛点击可唤醒的人工验收；不再依据合成事件失败判定产品唤醒功能失效，也不为自动化结果直接修改accept_first_mouse。

人工反馈未给出精确延迟、重复点击或其他边缘结果，不扩大范围。自动化最后两轮证据分别保存在 sequence-retry/run-1789289109841 与 active-control/run-1789289130122 子目录（完整目录前缀沿用上述证据表）；失败与人工反馈并存，合成输入路径单独待定位。本轮工具开始使用独立子目录避免重复覆盖历史截图。
