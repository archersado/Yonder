# Windows 原生窗口、空闲停靠与资源验证

## 结论

部分通过并发现失败。当前桌面进程能够创建真实 Windows 原生窗口、保持响应、进入空闲停靠展示状态并通过可访问按钮触发唤醒；但停靠与唤醒的原生窗口几何没有按设计改变，五分钟进程树资源读数也明显高于优化目标。本证据不通过完整 DS-S1、Windows 原生门禁或 AD-E0-01。

## 原生窗口与边界

- 启动进程 PID 64608，主窗口类名 `Tauri Window`、标题 `Yonda`、可见且置顶；初始原生矩形为 `(1965,621)-(2165,821)`，尺寸 200×200。
- 同进程创建 Task Space、语音输入、圈选提问、Jev 设置与 Agent 管理窗口，均为默认隐藏；主进程拥有 TCP 连接数为 0。
- 超过三分钟无交互后，可访问按钮名称变为“点击趴在边缘的Yonda唤醒它，Agent未连接”，证明前端进入 `docked` 状态。窗口移动到右下边缘 `(2352,1021)-(2552,1221)`。
- 失败：设计要求右侧停靠窗口缩为 56×112，但原生窗口仍为 200×200。
- 通过标准 UI Automation `InvokePattern` 调用 `pet` 按钮后，可访问名称恢复为“轻点Yonda小龙，按住移动可拖动，Agent未连接”，进程继续响应。
- 失败：唤醒后窗口仍停留在 `(2352,1021)-(2552,1221)`，没有恢复到停靠前位置。产品命令对前端返回成功，但 Windows 原生几何与设计不一致，应返回实施阶段定位。

本轮没有截取桌面，避免记录屏幕隐私；原生 Win32 窗口枚举、UI Automation 名称和结构化日志满足本次系统交互取证。仍缺真实视觉内容、透明边缘、人工拖动和用户物理点击证据。

## 五分钟资源样本

- 连续 305.317 秒，每 5 秒采样，共 53 个有效点；进程树最多 13 个进程，包括宿主、WebView2 子进程及控制台宿主。
- 工作集求和平均 857.08 MiB、峰值 863.50 MiB、P95 863.27 MiB。
- 进程树累计 CPU 按既有单核 100% 口径换算，平均 31.3848%、峰值 48%；按本机 24 个逻辑处理器归一后的平均值为 1.3077%。首次脚本输出使用了整机归一口径，验证后已修正脚本字段，本文保留两种口径避免混淆。
- 当前研发阶段性能预算按 Accepted 用户变更属于优化目标，不阻断已验证功能推进；但本样本不能标记 `<1% CPU / <150 MB` 达标，且相较既有 macOS 子范围读数存在明显差距。
